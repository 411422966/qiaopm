# 企业级 AI 原生 SaaS 产品研发方法论

> 版本：v2.1 | 日期：2026-08-01
> 适用：SaaS 产品 / 管理后台 / 中后台业务系统
> 来源：美业 SaaS 项目实战沉淀 + 企业级研发最佳实践
> 核心理念：**产品驱动 × 技术托底 × 模块闭环 × AI 加速 × 质量前置**

## 📌 文档通用性声明（跨项目使用指南）

**本方法论不绑定任何具体行业 / 项目**，是一套可直接复用于"SaaS 产品 / 管理后台 / 中后台业务系统"的通用研发方法论。

- **适用对象**：任何需要长期演进的业务系统（含 SaaS、CRM、ERP、运营后台、行业管理系统等）
- **不适用对象**：纯前端活动页 / 单页工具 / 一次性脚本 / 硬件固件
- **配套使用**：与 `MODULE-TEMPLATE-项目模块开发验证体系模板.md` 配合使用 —— 本文档讲"为什么 / 用什么原则"，模板讲"怎么做 / 步骤清单"
- **行业差异处理**：通用部分直接复用，行业特殊部分（支付 / 营销 / 课程 / 设备等）作为"特性包"自行补充，模板已预留扩展点
- **快速上手**：新项目只需复制模板 → 替换 `[项目名]` 等占位符 → 填写模块清单 → 即可开干，无需重读方法论

## Phase 0：产品定义（最重要的阶段）

> **"方向不对，努力白费"。Phase 0 解决的是'做对的事'，其余阶段解决的是'把事做对'。**

### 0.1 市场分析：回答四个灵魂拷问

不要写商业计划书。只回答四个问题：

```
问题 1：用户是谁？
        例：美容院老板 / 美发店老板娘 / 美甲店主
        → 不要写"所有美业商家"，越具体越好

问题 2：为什么买？（痛点 → 价值）
        例：会员流失率高 → 提高复购率
        例：预约混乱 → 减少爽约率
        → 核心价值不是"管理会员"，而是"解决生意问题"

问题 3：为什么选你？（差异化）
        例：操作简单 / 价格低 / 功能深 / 服务好
        → 第一版必须有一个明确差异点，不要做"全能选手"

问题 4：为什么现在做？
        例：疫情后数字化需求爆发
        例：竞品体验差且价格贵
        → 没有"为什么现在"，项目很容易半途而废
```

### 0.2 MVP 三层划分（克制是美德）

**90% 的项目失败，是因为第一版功能太多。**

```
┌─────────────────────────────────────────────────────────────┐
│                    MVP 三层划分                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ① 必须功能（Must Have）── 上线的最低门槛                   │
│     例：登录 / 会员管理 / 收银                               │
│     → 没有这些，客户不会用                                │
│                                                             │
│  ② 应该功能（Should Have）── 体验明显提升                  │
│     例：预约管理 / 储值卡 / 套餐次卡                         │
│     → 有这些，客户觉得值这个价                              │
│                                                             │
│  ③ 以后功能（Later）──── 有空再做                          │
│     例：AI 排班 / 数据报表 / 营销自动化                      │
│     → 记在 Roadmap 里，不要放进第一版                        │
│                                                             │
│  经验法则：Must Have ≤ 5 个核心流程                        │
│            Should Have ≤ Must Have × 3                      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 0.3 成功指标（没有目标就会无限开发）

**上线前必须定义"什么是成功"。**

```
┌─────────────────────────────────────────────────────────────┐
│                   上线 30 天成功指标                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  业务指标                                                    │
│  □ 签约商户数：10 家（或其他数字）                          │
│  □ 活跃会员数：1000 人                                      │
│  □ 日均订单量：100 单                                        │
│  □ 月收入：X 万元                                            │
│                                                             │
│  产品指标                                                    │
│  □ 核心流程完成率：≥ 80%                                    │
│  □ 用户 7 日留存：≥ 40%                                     │
│  □ 崩溃率：≤ 0.1%                                          │
│  □ API 平均响应时间：≤ 500ms                                 │
│                                                             │
│  运营指标                                                    │
│  □ 客服工单数：≤ 50 单/月（早期）                           │
│  □ NPS 净推荐值：≥ 30（上线 60 天后）                       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

> **没有指标的项目 = 不知道何时算完成 = 无限延期。**

### 0.4 PRD 怎么写（不是汇报材料，是施工图）

PRD 不是给领导看的 PPT，是给开发团队看的施工图。必须包含：

| 章节 | 核心问题 | 输出物 |
|---|---|---|
| 背景与目标 | 为什么要做？ | 一段话 + 成功指标 |
| 用户与场景 | 谁用？何时用？ | 角色 + 场景描述 |
| 功能清单 | 做什么？ | M01/M02/M03... + P0/P1/P2 |
| 业务流程 | 怎么做？ | 流程图 + 文字描述 |
| 数据模型 | 涉及哪些数据？ | ER 图 + 字段定义 |
| 状态机 | 对象有几态？谁触发？ | 状态流转图 |
| 非功能需求 | 性能/安全/多端？ | 量化指标清单 |

## Phase 1：产品设计

> **设计先行，编码后动。很多团队直接画 UI，实际上顺序反了。**

### 1.1 信息架构（IA）：页面之间的关系

**先规划信息架构，再画页面。**

```
例：美业 SaaS 信息架构

工作台
  └─ 今日看板

会员管理
  ├─ 会员列表
  ├─ 会员详情
  │   ├─ 基本信息
  │   ├─ 储值记录
  │   ├─ 套餐次卡
  │   └─ 消费历史
  └─ 新增会员

预约管理
  ├─ 日历视图
  ├─ 预约列表
  └─ 排班管理

收银台
  └─ 订单列表

库存管理
  ├─ 商品列表
  ├─ 入库
  └─ 盘点
```

**为什么先做 IA？**
- 让所有人对齐"有哪些页面"
- 避免遗漏 / 重复设计
- 后续做权限、菜单、导航都基于 IA

### 1.2 页面流程（User Flow）

**用户完成一个任务，依次经过哪些页面？**

```
例：会员充值流程

[会员列表] → 点击会员 → [会员详情] → 点击"储值"
    → [充值弹窗] → 选择金额 → 选择支付方式
    → [支付中...] → [支付成功] → [储值记录更新]
```

### 1.3 交互流程（微交互 + 表单校验）

对每个关键操作，定义：

```
操作：新建会员

输入字段：
  ├─ 姓名（必填，最长20字）
  ├─ 手机号（必填，11位正则校验）
  ├─ 性别（单选）
  ├─ 生日（可选，日期选择器）
  └─ 会员等级（下拉，关联基础数据）

交互细节：
  ├─ 必填项：实时校验（离开字段时触发）
  ├─ 手机号：实时查询是否已存在（防重复）
  ├─ 提交：Loading 状态（防重复提交）
  └─ 成功：关闭弹窗 + 列表刷新 + Toast 提示
```

### 1.4 领域模型分析（PRD → 数据表的翻译器）

**从需求直接跳到表结构，容易丢失关键业务逻辑。** 在 1.3 交互流程和 1.5 原型设计之间，插入轻量级领域建模——不需要完整 DDD，只做三件事：

```
┌──────────────────────────────────────────────────────────────┐
│                   领域模型分析（轻量版）                         │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  第一步：识别核心实体（Entity）                                 │
│    → 业务主体：有唯一标识，有生命周期                            │
│    → 例：会员 Member / 订单 Order / 预约 Booking               │
│                                                              │
│  第二步：识别值对象（Value Object）                             │
│    → 没有唯一标识，只是一组属性                                 │
│    → 例：地址 Address（省+市+区+详细）/ 金额 Money（数值+币种）│
│    → 例：时间段 TimeSlot（start~end）/ 手机号 Phone           │
│                                                              │
│  第三步：画业务关系草图（聚合根 + 子实体）                       │
│    → 聚合根（Aggregate Root）：外部引用的入口                  │
│    → 子实体：从属于聚合根，不能独立存在                         │
│    → 例：订单 Order（聚合根）→ 订单明细 OrderItem（子实体）  │
│    → 例：会员 Member（聚合根）→ 会员钱包 Wallet（1:1）        │
│                                                              │
│  识别原则：                                                    │
│    □ 一个操作是否需要同时修改多个表？ → 这些表可能是同一聚合      │
│    □ 某实体是否可以独立被引用？ → 可能是聚合根                  │
│    □ 某数据是否只是描述性属性？ → 可能是值对象                  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**领域模型 → 数据表的映射规则**：

| 领域模型 | 映射到 | 说明 |
|---|---|---|
| 聚合根 | 主表 + 主键 | 外部引用的入口 |
| 子实体 | 从表 + 外键 | 随聚合根一起删除 |
| 值对象 | JSON 字段 或 独立表 | 看查询频率和索引需求 |
| 枚举值 | 字典表 / tinyint | 禁止硬编码 ENUM |

**示例：美业 SaaS 核心领域模型**

```
会员 Member（聚合根）
  ├─ 钱包 Wallet（1:1，从属Member）
  ├─ 储值流水 WalletTransaction（1:N，属于Member）
  ├─ 套餐购买 PackageOrder（1:N，属于Member）
  │   └─ 核销记录 Redemption（1:N，属于PackageOrder）
  ├─ 预约 Booking（1:N，Member发起）
  │   └─ 技师 Schedule（被Booking引用，非从属）
  └─ 订单 Order（1:N，Member产生）
      ├─ 订单明细 OrderItem（N:1，属于Order）
      └─ 支付记录 Payment（N:1，属于Order）
```

**效果**：
- 数据表设计有依据，不会"订单表和预约表字段互相乱引"
- Service 层写业务逻辑时，能复用领域对象而非纯 CRUD
- 后续性能优化（索引/缓存）也基于领域边界来做

### 1.5 原型设计

**低保真原型 → 开发确认 → 高保真 UI**

| 工具 | 适用场景 |

### 2.3 API 设计规范

**接口规范在 Phase 2 就必须定死，不要等到联调阶段再改。**

#### RESTful 风格约定

```
资源：/members（会员列表）
      /members/{id}（单个会员）
      /members/{id}/wallet（会员储值）

HTTP 方法：
  GET    /members         列表（支持分页）
  GET    /members/{id}    详情
  POST   /members         新增
  PUT    /members/{id}     更新
  DELETE /members/{id}     删除

过滤/排序：
  GET /members?status=1&level_id=2&sort=created_at,desc&page=1&pageSize=20

批量操作：
  POST /members/batch-delete   批量删除
  POST /members/batch-update  批量更新
```

#### 统一响应格式

```json
{
  "code": 200,
  "message": "success",
  "data": { ... }
}
```

#### 分页格式

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "list": [...],
    "total": 100,
    "page": 1,
    "pageSize": 20
  }
}
```

#### 错误码规范

##### HTTP 状态码（框架层）

| Code | 含义 | 前端处理 |
|---|---|---|
| 200 | 成功 | — |
| 400 | 参数错误 | 显示字段错误 |
| 401 | 未登录 | 跳转登录页 |
| 403 | 无权限 | 显示"无权限" |
| 404 | 资源不存在 | 显示"记录不存在" |
| 409 | 业务冲突（如手机号已存在） | 显示具体冲突信息 |
| 500 | 服务器错误 | 显示"服务异常" + 上报 |

##### 业务错误码（errorCode，Phase 2 必须定义）

**为什么要单独定义 errorCode？** "余额不足"写成 message 字符串，前端无法精准处理——不同场景的"余额不足"可能需要不同交互。通过 errorCode 枚举，前端只判断 code，不匹配字符串。

```java
// 后端统一异常枚举（示例）
public enum BizCode {
    // 格式：模块_错误类型（大写下划线）
    MEMBER_NOT_FOUND("MEMBER_NOT_FOUND", "会员不存在"),
    MEMBER_PHONE_EXISTS("MEMBER_PHONE_EXISTS", "手机号已注册"),
    MEMBER_INSUFFICIENT_BALANCE("MEMBER_INSUFFICIENT_BALANCE", "余额不足"),

    ORDER_NOT_FOUND("ORDER_NOT_FOUND", "订单不存在"),
    ORDER_STATUS_NOT_ALLOWED("ORDER_STATUS_NOT_ALLOWED", "当前状态不允许此操作"),
    ORDER_PAID_TIMEOUT("ORDER_PAID_TIMEOUT", "订单支付超时"),

    BOOKING_TIME_CONFLICT("BOOKING_TIME_CONFLICT", "预约时间已被占用"),
    BOOKING_EMPLOYEE_UNAVAILABLE("BOOKING_EMPLOYEE_UNAVAILABLE", "技师该时段不可预约"),

    WALLET_RECHARGE_AMOUNT_INVALID("WALLET_RECHARGE_AMOUNT_INVALID", "充值金额必须大于0"),
    WALLET_REFUND_EXCEED("WALLET_REFUND_EXCEED", "退款金额超出实际支付");

    private final String code;
    private final String message;

    BizCode(String code, String message) {
        this.code = code;
        this.message = message;
    }
}
```

**统一响应格式升级版**（每个 API 必须带 traceId）：

```json
// 成功响应
{
  "code": 200,
  "message": "success",
  "data": { ... },
  "traceId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}

// 业务异常响应
{
  "code": 400,
  "message": "余额不足",
  "data": null,
  "errorCode": "MEMBER_INSUFFICIENT_BALANCE",
  "traceId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}

// 参数校验失败
{
  "code": 400,
  "message": "参数校验失败",
  "data": [
    { "field": "phone", "message": "手机号格式不正确" },
    { "field": "amount", "message": "金额必须大于0" }
  ],
  "errorCode": "VALIDATION_ERROR",
  "traceId": "..."
}
```

**前端处理规范**：

```
前端只判断 errorCode，不做 message 字符串匹配：

switch (errorCode) {
  case 'MEMBER_INSUFFICIENT_BALANCE':
    showRechargeDialog()    // 引导充值
    break
  case 'MEMBER_PHONE_EXISTS':
    showLoginInstead()      // 引导已注册用户登录
    break
  case 'ORDER_PAID_TIMEOUT':
    showRenewOrder()        // 引导重新下单
    break
  default:
    showErrorToast(message) //兜底
}
```

**规范约束**：
- errorCode 格式：`模块_错误类型`，全大写下划线
- 禁止硬编码字符串写 message，全部走枚举
- traceId 用于链路追踪，异常日志必须带上
- 每个模块定义自己的 BizCode 枚举，放在 `module/xxx/common/BizCode.java`

#### 幂等性

所有写操作（POST/PUT/DELETE）必须考虑幂等：
- 用唯一 ID（订单号 / 流水号）防止重复提交
- DELETE 软删（不真正删除数据）
- POST 退款等操作：先查是否已处理，再决定是否处理

### 2.4 数据设计

**Phase 2 必须输出 ER 图，不只是建表。**

#### ER 图核心要素

```
会员 Member
  ├─ id (PK)
  ├─ tenant_id      ← 多租户必加
  ├─ member_no      ← 唯一编号
  ├─ name, phone
  ├─ level_id (FK)  → 关联会员等级
  ├─ status         ← 状态字典
  ├─ created_at
  └─ updated_at

会员等级 MemberLevel
  ├─ id (PK)
  ├─ tenant_id
  ├─ name, level, discount

储值钱包 Wallet
  ├─ id (PK)
  ├─ member_id (FK → Member, UNIQUE)
  ├─ balance
  ├─ total_recharge
  └─ total_consume

储值流水 WalletTransaction
  ├─ id (PK)
  ├─ member_id (FK → Member)
  ├─ type              ← 1充值 2消费 3退款
  ├─ amount
  ├─ balance_before
  └─ balance_after
```

#### 数据库设计原则

| 原则 | 说明 | 示例 |
|---|---|---|
| **主键** | 统一用 `id bigint auto_increment` | — |
| **租户隔离** | 每个表加 `tenant_id` | 多商户 SaaS 必备 |
| **软删除** | 用 `deleted` 字段而非 `DELETE FROM` | `UPDATE SET deleted=1` |
| **时间戳** | 每个表有 `created_at` 和 `updated_at` | 自动维护 |
| **状态字典** | 用 `status tinyint`，不用 ENUM | 业务字典会扩展 |
| **索引** | 高频查询字段加索引 | `INDEX idx_phone(phone)` |
| **字段冗余** | 查询性能敏感时允许字段冗余 | `member_name` 冗余到订单表 |

## Phase 4：模块开发（核心）

> 这是整套方法论最精华的部分——**模块闭环开发**。Phase 4 的思想来自 v1.0，是经过实战验证的核心能力。

### 4.1 最小可运行单元（MRU）

**每个模块 = 数据库 + 后端 API + 前端页面，三者全通才算完成。**

```
┌─────────────────────────────────────┐
│  ┌──────────┐    ┌──────────┐     │
│  │   前端    │◀──▶│  后端 API │     │
│  │   Vue3   │    │SpringBoot │     │
│  └──────────┘    └─────┬─────┘     │
│                        │            │
│                  ┌─────▼─────┐     │
│                  │   MySQL   │     │
│                  │   数据库   │     │
│                  └───────────┘     │
│                                     │
│  ✅ 三者全通 = 模块验证完成          │
└─────────────────────────────────────┘
```

### 4.2 模块 5 步闭环

每个模块都按下面 5 步走，不跳步：

```
Step 1：明确边界
  ├─ 功能清单（做什么）
  ├─ 数据表（几张表？什么关系？）
  └─ API 列表（几个接口？）

Step 2：拆任务（4 阶段并行）
  ├─ 阶段 1：数据库（建表 + 索引 + 测试数据）
  ├─ 阶段 2：后端（实体 + Mapper + Service + Controller）
  ├─ 阶段 3：前端（API + 列表页 + 表单 + 路由）
  └─ 阶段 4：联调（前后端真实场景打通）

Step 3：同步推进（DB → 后端 & 前端并行）
  ├─ DB 建好后立刻给后端用
  ├─ 后端写好立刻给前端 mock
  └─ 前端写好立刻联调

Step 4：四层验证
  ├─ 数据库：SELECT/INSERT/UPDATE/DELETE 全跑通
  ├─ API：Postman 调通所有接口
  ├─ 前端：浏览器打开页面正常
  └─ 联调：真实业务场景跑一遍

Step 5：✅ 验收通过 → 进入下一个模块
```

| ESLint | JS/TS 规范 | 前端项目 pre-commit |
| Prettier | 代码格式化 | 前端 pre-commit |
| SpotBugs | Java 潜在 Bug | Maven plugin |

**配置到 CI 里，每次 PR 自动跑，不通过不让合并。**

### 5.4 安全检查

| 检查项 | 说明 |
|---|---|
| SQL 注入 | 使用参数化查询，不拼接 SQL |
| XSS | 前端转义，后端不过滤响应体 |
| 越权 | 校验当前用户对资源的操作权限 |
| 敏感数据 | 密码/Tel 不出现在日志/URL/响应中 |
| CORS | 只允许已知域名 |
| JWT | 验证签名 + 过期时间 |

### 5.5 模块间集成测试（冒烟测试）

**每个模块独立验证通过后，不代表模块之间能正确协作。** 模块间接口协议问题往往在联调阶段才暴露。

```
┌──────────────────────────────────────────────────────────────┐
│                   冒烟测试（Smoke Test）                      │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  目标：验证 P0 核心链路端到端能走通                          │
│  时机：所有模块独立验证完成后 / 上线前                        │
│  工具：Postman Collection Runner / HTTPie / curl 脚本         │
│                                                              │
│  美业 SaaS 冒烟测试用例：                                    │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ 用例 1：登录 → 创建会员 → 充值 → 支付 → 核销        │   │
│  │ 用例 2：登录 → 新建预约 → 签到 → 完成服务            │   │
│  │ 用例 3：登录 → 创建套餐 → 会员购买 → 核销            │   │
│  │ 用例 4：登录 → 创建员工 → 员工排班 → 预约该技师      │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  执行要求：                                                  │
│  □ 每个用例必须从登录开始（带 Token）                       │
│  □ 上线前必须跑通所有用例，失败则 BLOCK 上线               │
│  □ 用例数量控制在 5 个以内（只覆盖 P0 核心链路）            │
│  □ 结果记录到测试报告（哪怕是手动跑也要截图存档）           │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

> **注意**：冒烟测试不需要全自动化，但必须有人在上线前跑完、截图记录、通过审批。

## Phase 6：发布运维

> **上线不是终点，是开始。发布体系决定了你能不能睡好觉。**

### 6.1 环境分级

```
┌─────────────────────────────────────────────────────────────┐
│                    五环境分级                                 │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Dev      ── 开发自测，频繁提交，直接覆盖                     │
│     ↓                                                          │
│  Test     ── 功能测试，测试人员使用，数据独立                  │
│     ↓                                                          │
│  UAT      ── 用户验收测试，接近生产，必须走审批                 │
│     ↓                                                          │
│  Pre      ── 预发布/灰度，真实流量，限流/白名单                │
│     ↓                                                          │
│  Prod     ── 生产环境，受保护分支，强制 Code Review            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 6.2 CI/CD 流水线

```yaml
# .gitlab-ci.yml 或 Jenkinsfile
stages:
  - lint         # 代码检查
  - test         # 单元测试
  - build        # 构建镜像
  - deploy-test  # 部署 Test
  - deploy-uat   # 部署 UAT
  - deploy-pre   # 部署 Pre（可选灰度）
  - deploy-prod  # 部署 Prod（需手动触发）

deploy-prod:
  stage: deploy-prod
  when: manual    # 生产必须手动触发
  environment:
    name: production
```

### 6.3 灰度发布

**不要一次性全量上线。**

```
方案 A：按比例灰度
  初期 5% 流量 → 观察 1 小时 → 30% → 100%

方案 B：按用户群灰度
  先 A 类客户 → 再 B 类客户 → 再全量

方案 C：功能开关（Feature Flag）
  后端代码保留开关，上线后按需开启
```

### 6.4 回滚方案（必须在上线前准备好）

| 场景 | 回滚方式 |
|---|---|
| 数据库迁移失败 | 用 Flyway/Liquibase 回滚 SQL |
| 应用异常 | K8s 上一版本镜像 |
| 配置错误 | 配置中心回退配置 |
| 整体故障 | 切换流量到上一套环境 |

**回滚必须在 5 分钟内完成，脚本化，演练过。**

### 6.5 监控与告警

| 维度 | 指标 | 告警阈值 |
|---|---|---|
| 可用性 | 错误率 | > 1% |
| 性能 | API P99 响应时间 | > 2s |
| 资源 | CPU / 内存 | > 80% |
| 业务 | 订单量 / 登录失败数 | 偏离均值 50% |
| 安全 | 登录失败次数 | > 100 次/5 分钟 |

## Phase 7：商业运营

> **软件写完没人用 = 零价值。B 端 SaaS 真正的竞争力在运营。**

### 7.1 客户开通流程（SaaS 专属）

```
客户咨询
  ↓
开通租户（配置租户信息 / 绑定域名）
  ↓
初始化（导入数据 / 设置参数 / 配置支付）
  ↓
培训（操作手册 / 视频教程 / 客服 1v1 演示）
  ↓
正式上线（数据割接 / 通知用户）
  ↓
运营期（数据监控 / 问题响应 / 功能调研）
  ↓
续费 / 升级（价值呈现 → 商务谈判）
```

### 7.2 客户成功指标

| 指标 | 计算方式 | 目标 |
|---|---|---|
| 激活率 | 30 天内完成核心操作的用户 / 总用户 | ≥ 60% |
| 留存率 | 30 天后仍活跃的用户 / 总用户 | ≥ 40% |
| 续费率 | 合同到期续费客户 / 到期客户 | ≥ 80% |
| NPS | 净推荐值 | ≥ 30 |

### 7.3 反馈驱动迭代

```
客户使用 → 行为数据（埋点）
             │
             ├─ 功能 A 使用率低 → 分析原因 → 优化或下线
             ├─ 客户高频提某功能 → 记录 Roadmap
             └─ 客户遇到报错 → 立即修复

             ▼
产品反馈池（分类管理）
  ├─ Bug（立即修）
  ├─ 体验优化（下个版本）
  └─ 需求（下个版本 / Roadmap）
```

## 附录 C：技术债看板

> **承认不完美，但不遗忘。"以后再说"是技术债最大的来源。**

每个版本结束后，在此处更新技术债清单。目的是让技术债**可见、可控、可规划**。

```
| ID     | 模块   | 问题描述                                | 优先级 | 影响范围       | 计划版本 |
|--------|--------|----------------------------------------|--------|----------------|----------|
| TD-01  | M03    | 会员列表查询未走索引，1000会员时加载慢   | P2    | 性能          | v1.2     |
| TD-02  | M07    | 支付回调未做幂等处理，极端情况可能重复回调 | P1    | 资金安全      | v1.1     |
| TD-03  | 公共   | 统一响应封装未抽取公共模块，各模块各自实现  | P3    | 代码质量      | v1.3     |
| TD-04  | M04    | 储值流水表未分区，流水量过大会影响查询性能 | P2    | 性能          | v2.0     |
| TD-05  | 公共   | 日志格式不统一，排查问题困难              | P3    | 可维护性      | v1.3     |
```

**维护规则**：
- 每次版本发布后，更新此看板（新增 / 关闭 / 调整优先级）
- P1 必须排进下一版本，P2 排进近 3 个版本，P3 视情况安排
- Code Review 时发现新债，立即追加到此看板，不遗忘
- 技术债不得在代码里写 `TODO:` 而不登记到此看板

---

> **最后一句**：方法论是护栏，不是枷锁。**Phase 0~7 是完整地图，实际项目可以根据规模裁剪**——MVP 可以跳过 Phase 5/6 的部分细节，快速上线验证。但 Phase 0（产品定义）和 Phase 4（模块闭环）是不可跳过的核心，缺少这两个，项目失败概率翻倍。同时建议每个版本结束后更新附录 C 技术债看板，让债务真正被看见和管理，而不是遗忘在 TODO 注释里。
