## 1. 升级结论

### 1.1 总体判断

当前左侧菜单已经覆盖会员、储值、套餐、预约、收银、库存、提成、营销、报表和系统设置等主要经营域，**不需要推倒重做菜单**。需要进行的是一次“菜单信息架构 + 业务闭环 + 技术底座”的同步升级。

本次核验发现四类问题：

1. **菜单覆盖较完整，但 PRD 中的业务域没有全部落到菜单**：项目/疗程管理、评价回访、连锁管理、角色权限、房间/资源配置等能力缺少明确入口。
2. **文档状态与代码证据不一致**：`MODULE-模块化开发验证体系.md` 顶部写 M10/M11 已完成，但模块表又写“未开始”；M11 已有 Controller、前端页面和 `test-m11.ps1`，不能继续按未开始管理，也不能仅凭代码存在就宣称生产验收完成。
3. **页面存在但部分功能仍是占位或降级页**：库存消耗初始为未启用，多个库存页面的导出、批量打印、补货建议仍提示“开发中”。
4. **多租户、门店数据隔离、金额/库存/次数并发安全和统一错误码尚未达到技术方案宣称的企业级标准**：这是上线前必须优先修复的底座问题，优先级高于新增 AI 或复杂营销功能。

### 1.2 升级原则

- **先纠偏，再补闭环，最后做差异化**：先统一菜单、状态、接口和数据边界，再补项目/疗程、回访、连锁等核心能力。
- **模块化单体优先**：当前代码是 Spring Boot + MyBatis-Plus 的模块化单体，不建议在当前阶段直接拆微服务、引入 MongoDB/Elasticsearch/Kubernetes。
- **账务与库存以流水为准**：余额、积分、套餐次数、库存数量必须有可追溯流水，汇总字段只能作为缓存或查询优化。
- **所有写操作可重试但不能重复生效**：充值、扣款、退款、支付、核销、库存出入库、提成结算均需幂等。
- **权限来自后端，菜单来自权限**：前端静态菜单只能作为默认展示，不能作为安全边界。
- **“实现存在”与“验收通过”分开记录**：每个模块必须同时记录代码状态、接口测试状态、前端联调状态、业务验收状态。

## 2. 现状核验与差距

### 2.1 左侧菜单标准化清单

用户提供的菜单中存在“槠值/固/列脿/消粍/冥”等输入或识别错误。本方案统一采用以下产品名称：

| 一级菜单 | 二级菜单 | 推荐路由 | 现状判断 |
|---|---|---|---|
| 会员管理 | 会员管理 | `/member` | 已有页面和接口；建议继续扩展 360 画像、档案、消费/储值/套餐 Tab |
| 储值管理 | 储值充值、储值流水 | `/wallet/recharge`、`/wallet/transactions` | 已覆盖；需补充值审核、余额冻结、原路退款、门店/租户边界 |
| 套餐次卡 | 套餐管理、会员套餐 | `/package`、`/package/member-orders` | 已覆盖；需明确“套餐/次卡/疗程卡”模型和差价补款、转让审计 |
| 预约管理 | 预约日历、预约列表、排班管理 | `/booking/calendar`、`/booking/list`、`/booking/schedule` | 已覆盖；需补资源冲突、候补、爽约规则、跨店预约策略 |
| 收银结算 | 收银台、订单列表、收银统计 | `/pos/checkout`、`/pos/orders`、`/pos/stats` | 已覆盖；需补支付对账、部分退款、撤单逆向、发票/小票能力 |
| 库存管理 | 库存列表、商品耗材、出入库记录、消耗记录、盘点管理、库存预警、库存统计 | `/stock/*` | 页面和接口基本齐全；消耗、导出、补货建议、并发扣减仍需补强 |

| 系统设置 | 店铺配置、租户管理、操作日志、支付配置 | `/sys/*` | 已覆盖主要入口；建议增加角色权限、登录日志、房间资源、字典/参数配置 |

### 2.3 当前代码与文档状态差异

以下结论以当前工作区代码和测试脚本为证据，不能继续使用“12/12 全部完成”的表述：

- 前端 `src/router/index.ts` 已注册会员、储值、套餐、预约、收银、库存、提成、营销、报表和系统路由。
- 前端 `src/components/Layout.vue` 已展示大部分用户列出的二级菜单，但未展示“登录日志”、房间资源、角色权限、项目/疗程、评价回访、连锁管理。
- 后端已有 `StockController`、`CommissionController`、`ReportController`、`MarketActivityController`、`CouponController`、`PointController` 等 Controller，说明 M08-M11 具备实现基础。
- `test-m11.ps1` 已覆盖看板、日报、月报、支付方式、会员分析、员工绩效、报表配置和导出等接口，但不能替代前端 E2E、权限隔离、并发和数据正确性验收。
- `frontend/meiyetec-web/src/views/stock/consumption.vue` 的 `featureEnabled` 默认值为 `false`，且导出方法仍提示开发中；库存商品、出入库、库存预警页面也存在类似占位功能。
- `docs/MODULE-模块化开发验证体系.md` 第 180-195 行的模块状态表与文档顶部声明冲突，必须以统一状态模型重写。

### 3.2 菜单显示规则

| 角色 | 默认可见范围 | 必须限制 |
|---|---|---|
| 平台管理员 | 租户管理、租户级报表、平台配置 | 不直接操作门店经营数据，除非有审计授权 |
| 品牌总部 | 连锁管理、跨店会员、调拨、总部报表 | 不能修改平台级支付和租户套餐 |
| 店长 | 本店全部经营模块 | 只能访问所属门店；敏感支付凭据不可查看明文 |
| 收银员 | 会员查询、收银台、订单列表、有限退款 | 不能看工资、提成规则、租户信息 |
| 技师/员工 | 本人预约、服务记录、个人提成 | 不能访问全店储值流水、工资总表 |
| 财务 | 订单、支付、退款、对账、结算报表 | 不默认拥有会员档案全部敏感字段 |

前端菜单应由后端返回的 `menu permissions` 生成；按钮使用独立权限码，例如 `pos:refund`、`wallet:recharge`、`commission:confirm`。隐藏菜单不等于安全，后端必须二次校验租户、门店、角色和数据范围。

## 4. 升级技术架构

### 4.1 架构决策

| 决策项 | 当前方案 | v2.0 方案 | 说明 |
|---|---|---|---|
| 服务形态 | 文档倾向微服务，代码为单体 | **模块化单体** | 按领域分包，保留未来拆分边界；当前不引入分布式事务 |
| 后端 | Spring Boot 3.1.5 + MyBatis-Plus | 保持 Java 17，统一 Spring Boot 3.x 基线 | 先补测试和边界，不因版本升级引入额外风险 |
| 前端 | Vue 3 + Vite + Element Plus | 保持现有 Vue 3 + TypeScript + Element Plus | 抽取菜单、权限、导出、分页和状态组件 |
| 数据库 | MySQL | MySQL 8.0 为交易事实库 | 统一命名、索引、租户字段、软删除、版本号 |
| 缓存 | Redis | Redis 用于 Token 黑名单、幂等键、短期缓存、分布式锁 | 金额和库存最终事实仍在 MySQL |
| 文档库/搜索 | 方案提出 MongoDB/ES | 暂不引入 | 日志和会员档案先使用 MySQL + OSS；数据量达到阈值再评估 |
| 消息队列 | 方案提出 RabbitMQ/RocketMQ | 可选，先用事务事件表/异步任务 | 支付回调、导出、通知有明确异步需求时再接 MQ |
| 部署 | 方案提出 K8s | Docker Compose/单体容器起步 | 达到多租户规模和发布频率阈值后再 K8s 化 |
| 支付 | 多通道和数字人民币全量描述 | 支付通道适配层 + 可验证的通道状态 | 未取得真实通道资质和回调环境前，不宣称“数字人民币 2.0 全量完成” |

### 4.3 统一 API 规范

#### 4.3.1 请求与响应

所有新接口和改造接口统一使用：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {},
  "errorCode": null,
  "traceId": "20260808-abc123"
}
```

业务异常示例：

```json
{
  "code": 409,
  "message": "余额不足",
  "data": null,
  "errorCode": "WALLET_INSUFFICIENT_BALANCE",
  "traceId": "20260808-abc123"
}
```

- `200`：成功。
- `400`：参数校验失败。
- `401`：未登录或 Token 无效。
- `403`：无权限或数据范围不允许。
- `404`：资源不存在。
- `409`：业务冲突，如余额不足、预约冲突、重复退款。
- `500`：未知系统异常，不得把可预期业务错误统一返回 500。

现有 `Result.error(String)` 返回 500，需在公共层增加 `BizCode` 和统一异常处理；新接口不得继续依赖前端解析中文 `message` 判断业务分支。

所有业务表按实际情况统一具备：

```text
id, tenant_id, brand_id（连锁版可选）, store_id（门店业务必填）
status, deleted, version
created_by, created_at, updated_by, updated_at
```

流水表额外具备：

```text
business_no / idempotency_key / source_type / source_id / operator_id / remark
```

当前工程同时使用 `created_at/updated_at` 与 `create_time/update_time`，升级时以现有数据库实际字段为基线，制定迁移映射，禁止新表继续随意混用。

### 5.3 金额、次数、库存的事实规则

1. **储值**：`wallet_transaction` 是不可变事实；钱包余额更新必须在同一事务中完成，并用行锁或乐观锁防止并发覆盖。
2. **积分**：积分账户余额和积分流水必须同事务更新；消费积分必须校验余额，重复请求必须通过业务单号幂等。
3. **套餐**：剩余次数更新必须带 `version` 或条件更新 `remaining_times >= consume_times`；退款、冲正、转让必须生成反向业务流水。
4. **库存**：出库按 FEFO（先到期先出）扣批次；库存不足、重复提交、盘点确认必须具备明确状态机和幂等键。
5. **订单/支付**：支付回调以通道流水号唯一；回调可重复到达但只能记账一次；订单状态和支付状态禁止由前端直接指定。
6. **提成**：订单退款、套餐核销撤销后必须产生提成冲正，不能直接删除原提成记录。

## 6. 核心业务闭环设计

### 6.1 会员充值闭环

```text
会员选择
  → 读取会员/门店/活动规则
  → 创建充值订单（幂等键）
  → 发起支付或记录现金收款
  → 支付成功回调
  → 钱包余额 + 钱包流水 + 会员汇总 + 积分奖励
  → 生成操作日志和支付对账记录
  → 通知会员
```

验收重点：重复点击、重复回调、充值失败、部分退款、赠送金额、冻结余额、跨店充值权限。

### 6.2 预约到收银闭环

```text
预约创建
  → 校验门店/会员/项目/技师/房间资源
  → 锁定时间段
  → 确认/签到/开始服务
  → 完成服务
  → 创建订单或绑定已有订单
  → 次卡核销 / 储值扣款 / 混合支付
  → 生成库存消耗
  → 计算提成
  → 评价/回访任务
```

验收重点：技师和房间双冲突、跨午夜时段、取消和爽约、改期、候补补位、套餐核销失败回滚。

### 6.3 订单退款闭环

```text
申请退款
  → 校验订单状态、可退金额、原支付渠道
  → 生成退款单
  → 原路退款或储值返还
  → 反向恢复套餐次数/库存/积分（按退款策略）
  → 冲正提成
  → 更新订单与支付状态
  → 审计与对账
```

必须区分整单退款、部分退款、储值支付退款、现金退款、第三方支付退款；禁止直接把订单状态改为“已退款”而不记录逆向明细。

## 8. 非功能要求

### 8.1 性能

| 场景 | v2.0 目标 |
|---|---:|
| 普通列表接口 P95 | ≤ 300 ms（开发环境基线） |
| 会员/预约/订单核心查询 P95 | ≤ 500 ms |
| 充值、支付回调、扣款写操作 | ≤ 1 s 完成受理，异步任务另行处理 |
| 报表查询 | 明细范围受控；大报表异步化 |
| 导出 | 创建任务接口 ≤ 500 ms，文件异步生成 |
| 数据库慢查询 | 线上 SQL P95 < 500 ms；上线前完成 EXPLAIN |

当前 `ReportController` 采用拉取大量订单后在内存聚合的实现，需要改为按租户/门店/时间范围的 SQL 聚合或预聚合快照，避免数据量增长后拖垮应用。

### 8.2 安全

- 所有查询从 Token 解析 `tenantId`、`brandId`、`storeId` 和数据范围，禁止默认使用 `tenantId=1` 或 `storeId=1`。
- 会员手机号、身份证、银行卡、支付凭据、照片和资质文件按最小权限脱敏展示。
- 支付密钥和数字人民币凭据不进入日志、不进入前端明文响应、不使用默认密码。
- 关键操作记录操作者、租户、门店、IP、User-Agent、业务单号、前后值摘要。
- 文件下载必须校验租户归属和权限，不能只凭文件 ID 下载。
- 会员数据支持隐私授权、撤回授权、导出和删除/匿名化策略。

### 8.3 可观测性

统一记录：`traceId`、`tenantId`、`storeId`、`userId`、`businessNo`、接口耗时、数据库耗时、异常码。

告警最少覆盖：支付回调失败、重复回调、退款失败、库存负数、预约冲突异常、导出失败、登录异常、跨租户访问拒绝。

## 10. 发布门禁

只有同时满足以下条件，才可将“可上线运营”写入模块文档：

- [ ] 菜单、路由、接口、按钮权限四者一致。
- [ ] 租户和门店越权测试通过；至少使用两个租户、两个门店验证。

- [ ] 正向、参数异常、业务冲突、权限异常、回滚场景均有测试记录。
- [ ] 前端无“功能开发中”“未启用”但实际进入生产菜单的占位入口。
- [ ] 报表口径经产品和财务确认，金额可与订单/支付流水对账。

- [ ] 数据库迁移可重复执行或具备版本号、回滚方案。
- [ ] 后端构建、前端构建、集成测试、核心 E2E 测试全部通过。
